# Сценарии работы (playbooks)

> Статус: ✅ согласовано. Пошаговые сценарии для людей и ИИ-агентов. Общие правила — в [AGENTS.md](../../AGENTS.md).

## Definition of Ready

Задачу `Tx.y` можно начинать, когда:

- [ ] все задачи из колонки «Зависит от» в [IMPLEMENTATION_PLAN.md](../IMPLEMENTATION_PLAN.md) имеют статус ✅ в [STATUS.md](../STATUS.md)
      (или явно разрешено работать по контракту из открытого PR);
- [ ] открытые вопросы `Q`, блокирующие задачу, закрыты **или** команда согласна на значение по умолчанию;
- [ ] есть спецификация функции с разделами «API», «Валидация», «Критерии приёмки»;
- [ ] понятно, какие общие файлы будут затронуты, и второй разработчик предупреждён.

Если что-то не выполнено — сообщи пользователю, что именно, и не начинай реализацию.

## Definition of Done

Задача закрыта, когда:

- [ ] выполнено условие «Готово, когда» из IMPLEMENTATION_PLAN.md и критерии приёмки спецификации функции;
- [ ] `npm run lint`, `npm run typecheck`, `npm run test` зелёные (после Phase 0; e2e — для backend-задач);
- [ ] тесты покрывают правила доступа и бизнес-правила задачи ([TESTING.md](TESTING.md));
- [ ] при изменении API: API_CONTRACT.md обновлён, `npm run contract` выполнен;
- [ ] при изменении схемы: одна миграция по [CHANGE_PROCESS.md](CHANGE_PROCESS.md);
- [ ] спецификация функции соответствует реализованному поведению; закрытые `Q` отмечены в REQUIREMENTS.md;
- [ ] [QUALITY_CHECKLIST.md](../QUALITY_CHECKLIST.md) пройден;
- [ ] STATUS.md обновлён: статус задачи, ветка/PR, запись в журнале;
- [ ] PR влит в `main` после ревью второго студента.

## Playbook 1. Реализовать задачу `Tx.y`

1. STATUS.md → убедись, что задача ⬜ и не заблокирована; проверь Definition of Ready.
2. IMPLEMENTATION_PLAN.md → строка задачи: владелец, зависимости, «Готово, когда».
3. Спецификация функции → сценарии, права, валидация, ошибки, критерии приёмки.
4. API_CONTRACT.md → endpoint'ы задачи; DATA_MODEL.md → сущности.
5. Ветка от свежего `main`: `feat/<module>-<short>` (только по просьбе пользователя создать/переключить).
6. Порядок реализации для full-stack задачи:
   1. модель Prisma + миграция (если нужна) — по CHANGE_PROCESS.md;
   2. DTO → service (права, правила) → controller; юнит-тесты сервиса; e2e-тесты endpoint'ов;
   3. `npm run contract`;
   4. `features/<name>/api.ts` → компоненты → страницы; состояния загрузки/пусто/ошибка;
   5. тесты компонентов с логикой.
7. Проверка (Definition of Done), обновление документов и STATUS.md.
8. Итог пользователю: что сделано, что проверено, что **не** проверено, что дальше.

## Playbook 2. Изменить API-контракт

1. Определи тип изменения (таблица в [CHANGE_PROCESS.md](CHANGE_PROCESS.md#изменение-api-контракта)).
   Ломающее → остановись, предупреди пользователя.
2. Обнови API_CONTRACT.md (и таблицу соответствия, если затронута исходная операция).
3. Измени DTO/controller → `npm run contract` → `npm run typecheck` → исправь frontend своего модуля.
4. Обнови спецификацию функции и правила инвалидации (API_REQUEST_ARCHITECTURE.md §6.3), если нужно.

## Playbook 3. Изменить схему БД

1. Предупреди пользователя: `schema.prisma` — общий файл.
2. Обнови DATA_MODEL.md (сущности, ограничения, правила удаления).
3. `git fetch` + rebase на `main` → изменить схему → `npm exec -w api -- prisma migrate dev --name <name>`.
4. CHECK-ограничения — через `--create-only` и правку SQL (DATABASE_DECISIONS.md).
5. Прочитай сгенерированный SQL; запусти тесты.

## Playbook 4. Исправить ошибку

1. Воспроизведи: шаги, ожидаемое и фактическое поведение. Найди правило в спецификации функции.
2. Сначала тест, который падает из-за ошибки; затем исправление; тест зелёный.
3. Если «ошибка» — на самом деле неописанное поведение: не придумывай правило — спроси и дополни спецификацию.
4. Ветка `fix/<module>-<short>`; запись в STATUS.md (раздел «Известные проблемы», если исправлено не полностью).

## Playbook 5. Закрыть открытый вопрос `Qn`

1. Запиши ответ в таблицу REQUIREMENTS.md §5 (колонка «По умолчанию» → «Решено: …» с датой).
2. Найди все упоминания: поиск по `Qn` во всех `.md`. Обнови каждое место (контракт, модель, спецификации, план).
3. Если решение архитектурное — ADR.
4. Добавь строку в STATUS.md §5 «Закрытые вопросы».

## Playbook 6. Добавить технологию или зависимость

1. Проверь ARCHITECTURE.md §6: есть ли условие, при котором технология оправдана, и выполнено ли оно.
2. Объясни пользователю: зачем, альтернатива без неё, цена. Жди одобрения.
3. Новая инфраструктура или общее соглашение → ADR. Обычная библиотека → обоснование в описании PR.
4. Ставить из корня: `npm install <pkg> -w <app>`.

## Playbook 7. Ревью PR

1. Задача PR соответствует строке IMPLEMENTATION_PLAN.md и владельцу модуля.
2. Пройди QUALITY_CHECKLIST.md; особое внимание: права доступа, общие файлы, сгенерированные файлы не правлены руками.
3. Документы обновлены в том же PR (спецификация, контракт, STATUS.md).
4. Замечания: блокирующие — явно помечены; остальные — пожелания.

## Playbook 8. Начало и конец сессии (передача дел)

**Начало:**
1. Прочитай STATUS.md: §1 «Коротко», доска задач, верхние записи журнала.
2. `git status` и текущая ветка: есть ли незакоммиченная работа предыдущей сессии.
3. Сверь с пользователем задачу сессии.

**Конец:**
1. Обнови статус задач на доске STATUS.md.
2. Добавь **сверху** строку в журнал STATUS.md §7: дата, кто, что сделано (с указанием «не закоммичено», если так),
   что дальше.
3. В сообщении пользователю: результат, что не проверено, следующий шаг.

Журнал — главный механизм передачи контекста между сессиями: следующий агент не видит ваш разговор,
он видит только репозиторий.
