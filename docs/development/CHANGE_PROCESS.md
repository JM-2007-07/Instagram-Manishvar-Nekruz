# Процесс изменения контракта и схемы БД

Два самых конфликтных места проекта — **API-контракт** и **`schema.prisma`**: их используют оба
разработчика. Этот документ описывает, как менять их без поломок.

## Изменение API-контракта

Источник истины — DTO и контроллеры NestJS → Swagger → `docs/api/openapi.json` → типы frontend.

### Когда нужно согласование
| Изменение | Согласование |
|---|---|
| новый endpoint в своём модуле | достаточно ревью PR |
| новое **необязательное** поле в ответе | достаточно ревью PR |
| изменение/удаление поля, пути, метода, кода ошибки, обязательности | **сначала** сообщение второму разработчику, затем PR |
| изменение общих соглашений (формат ошибок, пагинация, cookie) | ADR + согласование обоих |

### Шаги
1. Обновить файл модуля `docs/api/endpoints/<module>.md` (и [API_CONTRACT.md](../api/API_CONTRACT.md) — если меняются
   соглашения или общие модели §1.4; [REALTIME.md](../api/REALTIME.md) — если меняются события).
2. Реализовать изменения в DTO/контроллере NestJS.
3. `npm run contract` — обновит `docs/api/openapi.json` и `apps/web/src/lib/api/schema.d.ts`.
4. `npm run typecheck` — исправить места во frontend, которые сломались (если это ваш модуль) или
   договориться с владельцем модуля.
5. Всё это — **в одном PR**, с отметкой в шаблоне PR «контракт изменён».
6. Никогда не редактировать `openapi.json` и `schema.d.ts` вручную.

### Конфликты в сгенерированных файлах
При конфликте слияния в `openapi.json` или `schema.d.ts` — не править вручную: взять версию `main`,
затем заново выполнить `npm run contract` на своей ветке.

## Изменение `schema.prisma` и миграции

### Правила
1. Перед изменением схемы — сообщение второму разработчику: «меняю схему: добавляю модель X / поле Y».
   Одновременно в работе — **не более одного** PR с миграцией от каждого, и они не трогают одни и те же модели.
2. Модели своего модуля меняет владелец модуля. Связи с чужими моделями (например, `Post.locationId`) — по договорённости.
3. Один PR — одна миграция с понятным именем: `prisma migrate dev --name add_posts`.
4. Сгенерированный SQL (`migrations/<timestamp>_<name>/migration.sql`) коммитится и **читается на ревью**.
5. CHECK-ограничения и другие правила, которых нет в Prisma, — через `migrate dev --create-only` и правку SQL
   (см. [DATABASE_DECISIONS.md](../database/DATABASE_DECISIONS.md#ограничения-которых-нет-в-prisma-схеме)).

### Если `main` ушёл вперёд с новой миграцией
1. `git fetch && git rebase origin/main`.
2. Удалить **свою невлитую** папку миграции.
3. `npm exec -w api -- prisma migrate dev --name <то же имя>` — Prisma создаст миграцию поверх свежих.
4. Проверить SQL, запустить тесты, обновить PR.

### Запрещено
- Редактировать или удалять миграции, уже влитые в `main`.
- `prisma db push` для изменений, которые идут в `main` (только для экспериментов в своей БД).
- `prisma migrate reset` на чьей-либо БД, кроме своей локальной.
- Коммитить сгенерированный Prisma Client.

### Порядок первых миграций (Phase 1)
1. A: `User`, `Session`, `PasswordResetToken` → влито в `main`.
2. B: `MediaFile` (ссылается на `User`) → после шага 1.
