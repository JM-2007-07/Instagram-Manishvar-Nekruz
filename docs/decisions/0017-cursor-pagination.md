# 0017. Курсорная пагинация для всех списков

- Статус: Принято
- Дата: 2026-10-21
- Изменяет соглашение API_CONTRACT §1.3 (ранее — `page`/`limit` + `total`)

## Контекст

Ленты, комментарии, сообщения и уведомления постоянно пополняются новыми записями. При постраничной выдаче
(`page=2`) новые записи сдвигают страницы — пользователь видит дубли или пропускает элементы (Q29). Instagram везде
использует курсоры. Кроме того, `total` требует отдельного `COUNT(*)` на каждый запрос.

## Решение

- Все списки: `?cursor=<opaque>&limit=<1..50>` (по умолчанию 20).
- Ответ: `{ "items": [...], "nextCursor": "…" | null }`. `null` — больше нет.
- Курсор — непрозрачная строка (base64 от `createdAt` + `id` последнего элемента); клиент его не разбирает.
- Сортировка с уникальным «хвостом»: `ORDER BY createdAt DESC, id DESC`, условие «меньше курсора».
- Счётчики (подписчики, лайки, публикации) отдаются в самих объектах, а не через `total` списков.
- RTK Query: `initialPageParam: null`, `getNextPageParam: (last) => last.nextCursor ?? undefined`.

## Рассмотренные альтернативы

- **`page`/`limit`** — проще, но дубли и пропуски в живых лентах.
- **Два стиля** (страницы для одних списков, курсоры для других) — лишняя сложность.

## Последствия

- Параметры исходного Swagger `PageNumber`/`PageSize` заменяются курсором (таблица соответствия).
- Образцы в API_REQUEST_ARCHITECTURE.md и CODING_CONVENTIONS.md используют `nextCursor`.
