# 0019. TanStack Query — только для поиска аккаунтов

- Статус: Принято
- Дата: 2026-10-23
- Дополняет: [0010](0010-rtk-query.md) (RTK Query остаётся основным способом запросов)

## Контекст

Преподаватель потребовал показать на экзамене TanStack Query на одном реальном сценарии — поиске пользователей.
При этом в проекте уже один источник серверных данных — RTK Query (ADR 0010), и два кэша для одних и тех же
данных дали бы двойные запросы и рассинхронизацию.

## Решение

1. `@tanstack/react-query` подключён в `apps/web` **только** для поиска аккаунтов `GET /api/v1/search/users`.
2. Один `QueryClient` на вкладку — `QueryProvider` в `lib/query-client.tsx`, подключён в `app/layout.tsx`
   внутри `StoreProvider`.
3. Запрос и хук — `features/search/user-search.ts` (`fetchAccounts`, `useAccountSearch`): тот же same-origin
   адрес `/api/v1/...`, cookie сессии, отмена устаревшего запроса через `signal`, ключ `['search', 'users', q]`.
   Ошибка отдаётся в форме RTK Query (`{ status, data }`), поэтому `getApiError` и `ListError` работают без изменений.
4. Хэштеги и места в том же поиске — RTK Query (`findHashtags`, `findLocations` в `features/search/api.ts`).
   Общий `GET /search` (аккаунты + хэштеги + места) поиском больше не используется, чтобы аккаунты
   не запрашивались дважды.
5. Всё остальное — RTK Query. Новые запросы через TanStack Query — только новым ADR.

## Рассмотренные альтернативы

- **Перевести на TanStack Query весь frontend** — большой риск перед экзаменом, переписывание всех `features/*/api.ts`.
- **Оставить только RTK Query** — не выполняет требование преподавателя.

## Последствия

- Поиск аккаунтов не попадает в кэш RTK Query: после подписки из результатов поиска кнопка обновляется
  своим состоянием (`FollowButton`), а не повторным поиском.
- В тестах компонента поиска нужен `QueryClientProvider` (`makeQueryClient()`).
