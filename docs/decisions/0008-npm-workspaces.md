# 0008. npm workspaces вместо pnpm

- Статус: Принято
- Дата: 2026-10-21
- Заменяет: [0001](0001-monorepo-pnpm.md) (в части менеджера пакетов)

## Контекст

В ADR 0001 был выбран pnpm. Команда решила перейти на npm: он уже установлен вместе с Node.js,
не требует `corepack enable` и знаком обоим студентам — меньше инструментов, которые нужно объяснять.
Приложений и lockfile ещё нет, поэтому переход ничего не стоит.

## Решение

- npm workspaces: поле `"workspaces": ["apps/*"]` в корневом `package.json`; файл `pnpm-workspace.yaml` удалён.
- npm 11 (идёт с Node.js 24), `packageManager: npm@11.12.1`, один корневой `package-lock.json`.
- Команды: `npm run <script> -w <api|web>`, `npm run <script> --workspaces --if-present`.
- Параллельный запуск `npm run dev` — пакет `concurrently` (у npm нет встроенного параллельного запуска).
- В CI — `npm ci`.
- Остальное из ADR 0001 не меняется: без Turborepo/Nx, без `packages/`.

## Чем платим и как компенсируем

npm поднимает зависимости в общий `node_modules` в корне, поэтому код одного приложения может
импортировать пакет, объявленный только в другом (pnpm это запрещал). Компенсация в Phase 0:

| Риск | Защита |
|---|---|
| импорт пакета, не объявленного в своём `package.json` | ESLint `import/no-extraneous-dependencies` в обоих приложениях |
| импорт кода из соседнего приложения (`../api/...`) | ESLint `no-restricted-imports` |
| случайный второй lockfile внутри приложения | `.gitignore` для `apps/*/package-lock.json` + правило «ставить зависимости из корня с `-w`» |

## Рассмотренные альтернативы

- **Оставить pnpm** — строже, но ещё один инструмент; строгость компенсируется правилами ESLint.
- **Yarn** — те же доводы, что против pnpm, без его преимущества строгости по умолчанию.

## Последствия

- Установка проекта: только Node.js 24 + `npm install`.
- Все документы используют команды npm. Упоминания pnpm остались только в ADR 0001 как история решения.
