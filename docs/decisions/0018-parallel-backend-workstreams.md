# 0018. Параллельный backend: многофайловая схема Prisma и заглушки общих сервисов

- Статус: Принято
- Дата: 2026-10-22
- Дополняет: [0011](0011-instagram-parity-scope.md) (порядок работ), ADR о структуре данных — [DATABASE_DECISIONS.md](../database/DATABASE_DECISIONS.md)

## Контекст

Два студента должны разрабатывать backend одновременно, не ожидая друг друга и не конфликтуя в общих файлах.
Главные источники конфликтов и ожидания:

1. **Один файл `schema.prisma`** — каждый модуль добавляет туда модели; параллельные PR конфликтуют.
2. **Межмодульные вызовы** — публикации (B) должны учитывать приватность (A), создавать уведомления (A),
   отправлять события (A); профиль (A) использует медиа (B). Если ждать готовых реализаций, потоки становятся последовательными.

## Решение

1. **Многофайловая схема Prisma** (стабильно с Prisma 6.7; в Prisma 7 — `schema: "prisma/schema"` в `prisma.config.ts`):
   файл `prisma/schema/<module>.prisma` на модуль, у каждого файла один владелец (таблица в DATA_MODEL.md §1).
   `base.prisma` (generator, datasource) и `account.prisma` (`User`, `Session`, `UserSettings`) — A.
   Обратные связи, которые Prisma требует на стороне `User`, второй студент добавляет в свой помеченный блок модели
   `User` — единственное разрешённое изменение чужого файла схемы.
2. **Заглушки общих сервисов с первого дня (C0).** `VisibilityService`, `NotificationsService`, `RealtimeService`,
   `SessionGuard`, `UserSummaryDto`, тестовые помощники создаёт владелец (A) в T0.3 как настоящие классы с простейшим
   поведением; позже владелец заменяет тела методов, сигнатуры не меняются. Это **не** вторая реализация: в коде
   всегда один класс; другой студент лишь вызывает его.
3. **Backend-first с личными контрольными точками.** Каждый начинает frontend своих модулей, когда его backend готов
   (MA-1 / MB-1), не дожидаясь завершения всего backend.
4. **Prisma ставится явно версии 7** (`prisma@7`, `@prisma/client@7`): на 2026-10-22 метка `latest` в npm указывает на 8.0.0-rc.

## Рассмотренные альтернативы

- **Один файл схемы + очередь изменений** — работает, но каждый PR с моделями блокирует другой; конфликты в одном файле.
- **Общий пакет с интерфейсами (`packages/contracts`)** — лишний уровень и сборка ради нескольких сигнатур; заглушки
  внутри модулей проще (ADR 0001).
- **Ждать реализаций** — потоки становятся последовательными.
- **Временные копии чужих модулей** — две реализации одного и того же, расхождение и путаница.

## Последствия

- Владельцы файлов схемы, правило обратных связей и порядок миграций — в CONTRIBUTING.md и CHANGE_PROCESS.md.
- До реальной реализации `VisibilityService` выдачи B не учитывают приватность; тесты приватности своих выдач B добавляет
  после T1.A5 (часть его Definition of Done).
- Проверить в T0.2 на установленной версии: генерация клиента видит модели из всех файлов (ошибка «указан файл, а не
  каталог» молча теряет модели).
