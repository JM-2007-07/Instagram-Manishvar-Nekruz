# 0014. Вход через Google и Facebook

- Статус: Принято (нужны приложения разработчика — Q32)
- Дата: 2026-10-21

## Контекст

В веб-Instagram есть «Войти через Facebook» ✅; команда добавляет ещё вход через Google. Сессии остаются серверными
(ADR 0003): провайдер подтверждает личность, а сессию выдаёт наш backend.

## Решение

1. **Authorization Code Flow с PKCE и `state`**, полностью на backend:
   `GET /api/v1/auth/oauth/{google|facebook}` → редирект к провайдеру → `GET /api/v1/auth/oauth/{provider}/callback`
   → проверка `state` и кода → получение профиля → вход или регистрация → наша cookie сессии → редирект на `/`.
   Все адреса — через same-origin прокси, поэтому cookie ставится на домен сайта.
2. **Google** — OpenID Connect (проверка `id_token`, `email_verified`); **Facebook** — OAuth 2.0 + Graph API
   (`id`, `name`, `email`, `picture`). Библиотека `openid-client` для Google, прямые HTTP-запросы для Facebook.
3. **Связь с аккаунтом:** таблица `OAuthAccount(provider, providerUserId, userId)`.
   - есть связь → вход;
   - нет связи, email провайдера подтверждён и совпадает с подтверждённым email пользователя → связать и войти;
   - иначе → регистрация: экран выбора имени пользователя и даты рождения, затем создание аккаунта.
4. Аккаунт без пароля (создан через соцвход) может задать пароль в настройках.
5. Ключи — `GOOGLE_CLIENT_ID/SECRET`, `FACEBOOK_APP_ID/SECRET` в `apps/api/.env`; адреса возврата регистрируются
   у провайдеров для `http://localhost:3000` (dev) и боевого домена.

## Рассмотренные альтернативы

- **Passport-стратегии** — скрывают простой поток за абстракциями; собственный контроллер на два провайдера понятнее.
- **Токены провайдера во frontend** — противоречит HttpOnly-сессиям.

## Последствия

- Нужны бесплатные аккаунты: Google Cloud (OAuth-клиент) и Meta for Developers (приложение Facebook Login) — Q32.
- Без ключей кнопки соцвхода скрыты (флаг в конфигурации), остальное приложение работает.
