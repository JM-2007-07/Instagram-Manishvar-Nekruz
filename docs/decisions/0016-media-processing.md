# 0016. Обработка медиа: sharp и ffmpeg, фоновая очередь

- Статус: Принято (BullMQ — после появления Redis, Q33)
- Дата: 2026-10-21
- Дополняет: [0007](0007-media-storage.md)

## Контекст

Карусели с видео, reels до нескольких минут, видео-истории и голосовые сообщения требуют: проверить длительность,
сделать превью-кадр, привести видео к формату, который проигрывают все браузеры, удалить EXIF (геолокацию) из фото
и сделать уменьшенные копии для сетки.

## Решение

1. **Изображения — `sharp`:** поворот по EXIF и удаление метаданных, копии по ширине 1080 и 320 px (WebP/JPEG).
2. **Видео и аудио — `ffmpeg`/`ffprobe`** (системная программа): длительность и размеры; превью-кадр; перекодирование
   видео в H.264/AAC MP4 (до 1080 px); голосовые — в AAC/M4A.
3. **Статус медиа:** `MediaFile.status` = `PROCESSING` → `READY` | `FAILED`. Пост/история с необработанным видео
   публикуется после готовности; клиент видит «Обработка…».
4. **Очередь:** сначала — простая очередь в процессе backend (`MediaProcessingService`, по одной задаче за раз,
   повтор при ошибке, перезапуск незавершённых при старте). Когда появится Redis (Docker, Q33) — замена на **BullMQ**
   без изменения API.
5. Те же задачи: удаление файлов-«сирот», физическое удаление истёкших историй из хранилища, отложенное удаление аккаунтов.

## Рассмотренные альтернативы

- **Без обработки** — видео с телефонов (HEVC, MOV) не проигрываются в части браузеров; EXIF раскрывает место съёмки.
- **BullMQ сразу** — нужен Redis, а Docker пока не установлен.

## Последствия

- Разработчикам нужно установить `ffmpeg` (бесплатно); путь — `FFMPEG_PATH` в `.env`.
- Обработка видео нагружает процессор — один параллельный процесс в разработке.
