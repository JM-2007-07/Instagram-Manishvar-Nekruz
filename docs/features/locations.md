# Локации

> ⚠️ **Назначение функции не определено исходным Swagger** (P17). Реализация — минимальная, по умолчаниям Q6 и Q20.
> Подробная проработка — после ответа команды.

## Назначение
Справочник адресов: город, регион (`state`), индекс (`zipCode`), страна — как в `AddLocationDto`.
Предположение 📝 (Q20): локацию можно указать у поста, как «место» в Instagram.

## Пользовательские сценарии (по умолчанию)
1. При создании поста — необязательный выбор локации из справочника с поиском (если Q20 подтвердит привязку).
2. На посте — подпись с городом и страной.
3. Администратор (Q6) управляет справочником; до решения справочник заполняется через seed.

## API
`GET /locations`, `GET /locations/{locationId}`, `POST /locations`, `PATCH /locations/{locationId}`,
`DELETE /locations/{locationId}` — [API_CONTRACT.md §2.8](../api/API_CONTRACT.md#28-locations-locations-module).

## Данные
`Location(city, state, zipCode, country)`; `Post.locationId?` (Q20), при удалении локации → `null`.

## Права доступа
Чтение — любой вошедший. Создание, изменение, удаление — `ADMIN` (Q6). Без роли администратора эти
операции не открываются обычным пользователям.

## Валидация 📝
Все четыре поля обязательны (как в исходной схеме), 1–100 символов. Фильтры списка — по вхождению без учёта регистра.

## Ошибки и пустые состояния
- Нет локаций по фильтру → «Ничего не найдено».
- Не-администратор пытается изменить → `403`.

## Зависимости
auth (роль). Привязка к постам — posts (владелец B согласует поле `Post.locationId` с A).

## Критерии приёмки
- [ ] Список фильтруется по любому из четырёх полей и пагинируется.
- [ ] Изменяющие операции доступны только `ADMIN`.
- [ ] Удаление локации не ломает посты.
