# Решения по базе данных

> Статус: ✅ согласованы PostgreSQL + Prisma; остальное — 📝 предложено в этом документе.

## СУБД и ORM ✅

- **PostgreSQL** — локальная установка у каждого разработчика (версия 18 у текущего разработчика;
  минимальная поддерживаемая — 16 📝). Docker не требуется.
- **Prisma 7** — многофайловая схема в `apps/api/prisma/schema/` (файл на модуль), миграции в `apps/api/prisma/migrations/`.
- Каждый разработчик использует **свою локальную БД** `instagram` и отдельную `instagram_test` для e2e-тестов.

## Идентификаторы

📝 **UUID для всех сущностей.** В исходном Swagger пользователи имели строковые id, остальные — `int32`.
Единый тип:

- убирает путаницу «где строка, где число» в DTO, путях и типах frontend;
- одна проверка в путях (`ParseUUIDPipe`);
- не раскрывает количество записей и не позволяет перебирать id подряд (основная защита — всё равно
  проверка прав).

Цена — длинные id в URL; для учебного проекта несущественно.

## Многофайловая схема ([ADR 0018](../decisions/0018-parallel-backend-workstreams.md))

Схема разбита на файлы по модулям (`apps/api/prisma/schema/<module>.prisma`, Prisma 7, стабильно с Prisma 6.7):
два студента добавляют модели параллельно, не конфликтуя в одном большом файле. Владельцы файлов — таблица в
[DATA_MODEL.md §1](DATA_MODEL.md#1-общие-правила). Обратные связи на `User` добавляются по правилу CHANGE_PROCESS.md.
Устанавливать `prisma@7` и `@prisma/client@7` явно: метка `latest` в npm указывает на предварительную версию 8.

## Профиль внутри `User`

📝 Поля профиля (`bio`, `pronouns`, `gender`, `avatarMediaId`, `isPrivate`) хранятся в `User`, без отдельной таблицы
`UserProfile`. Связь 1:1 добавила бы join и лишний код без выгоды. В API профиль остаётся отдельным представлением (`Profile`).
Настройки, которые нужны редко (тема, язык, кто может комментировать), — в `UserSettings` (1:1, модуль `settings`):
так `User` не разрастается, а `isPrivate` остаётся в `User`, потому что участвует почти в каждом запросе выдачи.

## Короткие коды публикаций

Публикации адресуются как в Instagram — `/p/{shortcode}/`, `/reel/{shortcode}/`. `shortcode` — 11 случайных символов
`[A-Za-z0-9_-]`, уникальный индекс; при совпадении — повторная генерация. UUID остаётся первичным ключом и в API.

## Регистр `userName` и `email`

📝 Значения приводятся к нижнему регистру в сервисе перед сохранением и поиском; уникальный индекс
по сохранённому значению. Это проще, чем расширение `citext`, и одинаково работает везде.

## Счётчики

📝 Вычисляются (`_count` в Prisma). Хранимые счётчики — только при доказанной проблеме производительности
(и тогда обновляются в той же транзакции). Исключение с самого начала — `Post.playCount`: воспроизведения не являются
уникальными записями, их нечего считать через `_count`.

## Чаты: таблица участников

Чаты бывают личными и групповыми (F-DM-03), поэтому участники хранятся в `ChatParticipant`, а не в двух колонках `Chat`.
Для личного чата уникальность пары обеспечивает поле `Chat.directKey` = `"<меньший userId>:<больший userId>"`
(уникальный индекс, `NULL` у групп). Личное состояние участника (прочитано до, без звука, «удалил у себя», запрос)
хранится в его строке `ChatParticipant`.

## Перечисления вместо отдельных таблиц

Типы уведомлений, сообщений, стикеров, жалоб — enum Prisma: их набор известен из каталога функций, а отдельные
таблицы-справочники усложнили бы запросы без пользы. Данные, специфичные для типа (вопрос опроса, варианты), — в поле JSON
с описанной в DTO формой.

## Ограничения, которых нет в Prisma-схеме

Некоторые правила Prisma не умеет описывать декларативно (CHECK-ограничения). Они добавляются
**вручную в SQL миграции** (`prisma migrate dev --create-only`, затем правка SQL) и дублируются проверкой
в сервисе, чтобы ошибка была понятной:

- `Follow`, `Block`, `Restrict`, `Mute`, `CloseFriend`: пользователь не может указать сам себя;
- `Story`: есть `mediaId` или `sharedPostId`;
- `PostUserTag`: `x`, `y` в диапазоне 0..1;
- `Chat`: `directKey` задан тогда и только тогда, когда `type = 'DIRECT'`.

Правила, которые нельзя выразить CHECK (ответ только на комментарий верхнего уровня, не больше 20 медиа в посте,
не больше 5 ссылок), проверяются **только в сервисе** и покрываются тестами.

Изменение 2026-10-21: прежние ограничения `Chat.user1Id < user2Id` и `Message.attachmentMediaId` заменены моделью
участников и `MessageMedia` (каталог функций, ADR 0011).

## Транзакции

Операции, меняющие несколько таблиц (создание поста с медиа, удаление аккаунта, сброс пароля с отзывом
сессий), выполняются в `prisma.$transaction`.

## Миграции и работа вдвоём

Полный процесс — [CHANGE_PROCESS.md](../development/CHANGE_PROCESS.md#изменение-schemaprisma-и-миграции). Кратко:

1. Файл схемы модуля меняет только его владелец; `base.prisma` и `account.prisma` — A; перед миграцией — сообщение второму.
2. Миграция создаётся командой `prisma migrate dev --name <описание>` **после** `git pull --rebase` свежего `main`.
3. Один PR — одна логическая миграция. Сгенерированный SQL коммитится и читается на ревью.
4. Если в `main` появилась новая миграция, пока ваш PR не влит: удалить свою **невлитую** миграцию,
   подтянуть `main`, создать миграцию заново. Влитые миграции **никогда** не редактируются и не удаляются.
5. `prisma migrate reset` — только на своей локальной БД.
6. Сгенерированный Prisma Client не коммитится (генерируется при установке/сборке).

## Начальные данные

`prisma/seed.ts` (Phase 1+): тестовые пользователи с известными паролями **только для локальной разработки**,
немного постов и подписок для демонстрации. Пароли тестовых пользователей хранятся в seed-файле,
а не в документации и не в чате.
